# Q4 firmware and home programming

Status: implemented engineering target, 24 September 2026. **Physical MCU, OLED, storage and battery testing remains required.** Quotes, purchases and manufacturing release remain paused. Q3 sources and frozen artifacts remain historical and unchanged.

## Target and interfaces

Q4 uses STM32L072CBT6 with factory ROM USB programming. The application uses an internal clock and keeps USB inactive; the ROM configures its own USB clock. All application load bytes, vectors and constants fit inside the first 64 KiB Flash bank. The small Stop entry/wake routine is copied from there to SRAM before use. The linker reserves at least 4 KiB of the 20 KiB RAM for stack headroom. The board retains SWD recovery. [ST reference manual RM0376](https://www.st.com/resource/en/reference_manual/dm00108281.pdf), [ROM bootloader AN2606](https://www.st.com/resource/en/application_note/an2606-stm32-microcontroller-system-memory-boot-mode-stmicroelectronics.pdf).

| Function | Contract |
|---|---|
| Increment | PA0, active low |
| Count reset / boot selection | PA1 and BOOT0 share SW2, active high, external pull-down |
| OLED reset / switched supply | PB0 push-pull while powered; PB1 active-high enable |
| OLED SPI2 | PB13 SCK, PB15 MOSI, PB12 CS, PB14 D/C |
| FRAM SPI1 | PB3 SCK, PB4 MISO, PB5 MOSI, PB8 open-drain CS |
| USB / debug | PA11/PA12 USB; PA13/PA14 SWD; separate NRST recovery switch |
| Reserved | PA4/PA5/PA6 do not control a battery bypass; PA8 is analog/no-pull NC |

PB0 and all four OLED bus pins become high impedance before module power is removed. The common-rail module uses a reset pull-down; open-drain reset would fail to release it. The FRAM pins start high impedance, and their internal pulls are explicitly disabled. PB8's external pull-up is supplied by the isolated FRAM rail.

## Counter and confidence

- Each qualified increment increases a saturating 0–99,999,999 counter once. The 8 ms debounce filter does not repeat a held key.
- Reset wins if both keys qualify together. Holding reset suppresses increments. A qualified first press after sleep counts.
- Inactivity causes display shutdown and then MCU Stop after 30 seconds. Release edges wake the filter without synthesizing a press.
- Timer and both-edge interrupts capture timestamped raw inputs into a 256-slot queue with 255 usable entries. The producers share one interrupt priority and cannot interrupt one another; foreground removes each sample with interrupts briefly masked.
- Queue overflow discards uncertain history, freezes increments and latches ERR. A fresh, debounced reset restores confidence only after a clean zero record has been committed and verified. A second gap cannot be cleared by completion of an older reset transaction. Holding increment across recovery creates no synthetic press.

Only the last verified storage value is passed to the display. Counting can run ahead of the displayed saved value while a write or frame is in progress. A sudden loss before commit can discard that pending value. This is a last-committed-value guarantee, not a promise to preserve an uncompleted physical press or survive arbitrary memory destruction.

## Persistence

The product uses **FM25V02A-GTR**, on SPI1 independently of the OLED's SPI2. The driver checks the JEDEC manufacturer/family/density identity, status/protection bits and write-enable latch. It never writes the status register to remove protection. Every access is bounded; failed transactions leave CS released and disable the failing peripheral. This memory's 2.0 V minimum provides useful margin below the MCU brownout threshold. Its 50 µs/V rise and 100 µs/V fall requirements apply at every point of the supply waveform. The board's isolated 68 Ω / 10 µF network still needs effective-capacitance and measured rail validation. [Infineon FM25V02A datasheet](https://www.infineon.com/assets/row/public/documents/10/49/infineon-fm25v02a-256-kbit-32k-8-serial-spi-f-ram-datasheet-en.pdf).

The journal uses 96 rotating 32-byte records in external addresses 0x0000–0x0BFF. Each includes a format identifier, sequence, count, fault flag, complements, CRC32 and final commit word. A save first invalidates the destination commit word, writes the payload in separate foreground steps, then commits and checks the complete record. The prior valid slot remains intact throughout. Interrupted writes recover the previous or completed new record. A damaged latest record can fall back to an older valid slot; total unreadable/unrecognized storage starts uncertain. First use therefore requires an explicit count-reset press instead of silently treating arbitrary factory FRAM contents as trustworthy zero.

The FRAM bus runs nominally at 500 kHz. A minimum 512-core-cycle guard follows CS release to accommodate the 100 kΩ pull-up and the specified ≤100 pF CS capacitance. Startup leaves pins passive for 20 ms, wakes a possibly retained sleeping memory, and waits another 2 ms before identification and journal loading. That extra wake is necessary after NRST, which can reset the MCU while FRAM remains asleep.

Before MCU Stop, a settled journal or a quiescent latched storage fault permits one attempt at the FRAM B9 sleep command. Wake begins with a dummy read transaction and waits 2 ms before storage access, exceeding the 400 µs recovery maximum. Input capture continues during this guard. Sleep-mode current is specified at up to 8 µA; complete-board sleep current has not been measured. [Infineon sleep timing](https://www.infineon.com/assets/row/public/documents/10/49/infineon-fm25v02a-256-kbit-32k-8-serial-spi-f-ram-datasheet-en.pdf).

A permanent read, transfer, write or verification failure freezes confidence but no longer keeps the processor waking every millisecond forever. After normal inactivity, with the journal/backend quiescent and display/ADC off, MCU Stop is allowed while retaining ERR and the last verified count in RAM. This is deliberately separate from a successful persistence acknowledgement. A failed FRAM sleep attempt releases CS and isolates SPI; FRAM standby current may remain because an unresponsive device cannot confirm sleep. No automatic fault retry or forced-awake loop runs. Increment wakes ERR without changing the count; a fresh debounced reset permits one bounded SPI/FRAM reinitialization and zero-commit attempt. Only verified commit clears ERR. A held reset does not repeatedly retry. If memory remains unavailable, recovery or repair is still required.

The EEPROM alternate maps those records to Bank2, 0x08080C00–0x080817FF. It issues one aligned word operation at a time, polls completion, checks errors/readback and yields to input between words. Bank1 execution avoids the same-bank stall described by ST. A stuck busy condition fails after 25 nominal ms without reading the busy bank. That alternate still prohibits Stop while either its active operation or the hardware FLASH BSY flag remains unresolved. The application freezes confidence after storage errors; a new reset requests recovery, while a wedged peripheral can require MCU restart. STM32L0 ECC is hardware-managed; software does not invent an ECC-status register. Read-access errors, record CRC/complements and readback checks provide the implemented detection. [ST nonblocking memory note AN4808](https://www.st.com/resource/en/application_note/dm00260799-writing-to-nonvolatile-memory-without-disrupting-code-execution-on-microcontrollers-of-the-stm32l0-and-stm32l1-series-stmicroelectronics.pdf), [RM0376](https://www.st.com/resource/en/reference_manual/dm00108281.pdf).

## Stop entry on all silicon revisions

ST ES0292 Rev8 section2.1.2 identifies a RevA (REV_ID0x1000) Flash wake race around external interrupt entry into Stop. Q4 applies the documented workaround on every revision: a whole SRAM-resident routine writes both PDKEYR keys, sets RUN_PD, executes DSB/ISB/WFI, clears RUN_PD after wake, then returns only after DSB/ISB. Maskable interrupts stay disabled until that routine returns. DSEEKOFF is cleared so hardware wakes Flash; ordinary Sleep never enables Flash power-down. The existing Range1 regulator setup also avoids the separate section2.1.3 condition. [ST ES0292](https://www.st.com/resource/en/errata_sheet/es0292-stm32l07xxxl08xxx-device-errata-stmicroelectronics.pdf), [ST power-down key definitions](https://raw.githubusercontent.com/STMicroelectronics/stm32l0xx-hal-driver/master/Inc/stm32l0xx_hal_flash.h).

The linker puts the complete routine and its literal pool in the initialized-RAM copy span, with word-aligned Flash load data. Build verification interprets the actual compiled straight-line Thumb instructions: both keys, RUN_PD set, barriers/WFI, RUN_PD clear, barriers/return; every instruction and literal fetch stays within that SRAM span and no helper calls are permitted. This is a bounded binary check, not a simulation of the silicon erratum or an observed physical wake. Real repeated near-edge key/Stop timing tests remain required.

## Display and voltage monitoring

The selected **HS96L01W4S03** module's page-6 drawing identifies **SSD1315**. Older prose in the same supplier PDF says SSD1306 and gives different dimensions. Firmware follows the drawing's controller and the module's command example: 128 × 64, A8 3F, DA 12, page addressing and 8D 14 charge-pump mode. SSD1315 confirms 8D 14 selects 7.5 V. Contrast is reduced from the example's CF to 10; this is not a measured current limit. The sample leaves IREF at its external-reference reset default. The document contains interface straps rather than a complete internal schematic, so fitted IREF and supply implementation remain exact-module qualification items. [Module supplier PDF](https://datasheet.lcsc.com/datasheet/pdf/c5dd235441558974950f13e140069537.pdf?productCode=C5139758), [Solomon SSD1315 Rev1.1](https://files.waveshare.com/upload/f/f0/SSD1315_1.1.pdf).

Startup holds reset for more than 250 ms after module enable, clears all eight RAM pages, enables the pump and then the display. Shutdown sends AE and 8D 10, waits 200 nominal ms, then isolates all signal pins and removes supply. Bus faults use reset, a discharge guard and bounded retry. Frames are divided into 16-byte chunks; stale frames are followed by the latest saved value. SPI reports local transfer completion; it provides no acknowledgement that the glass displayed those bytes. Physical pixels, startup orientation, interrupted shutdown and noise recovery must be observed on the actual module.

A nonblocking ADC service performs internal calibration and measures VREFINT using its factory calibration word. It allows 5 ms reference settling, samples for 160.5 cycles at nominal 2 MHz, rejects invalid calibration/ADC values and stale samples, and uses rising/falling hysteresis. Display thresholds are 3.080 V ON and 3.070 V OFF, defined in `rail.h`; the count and FRAM continue when display voltage is inadequate. Three acceptable samples are required to enable; one low sample disables. The nominal sample interval is about 10 ms. [STM32L072 datasheet, tables 28–29 and 66](https://www.st.com/resource/en/datasheet/stm32l072cb.pdf).

The voltage tests use a conservative ±2% estimate-error model covering the stated −40 to +85 °C range, factory-reference error, drift, conversion error and quantization. This is not an analog simulation or a measured calibration guarantee over arbitrary aging. Sampling cannot guarantee protection against unlimited droop between samples, sudden removal or the switch-on transient. The selected TLV76701DRVR network has a modeled regulated range of3.15136–3.25866V; at−2% ADC error its lower corner still exceeds3.080V. This removes the previous always-blank regulated corner. The regulator minimum, OLED switch drop and remaining transient margin still require joint measurement. Invalid ADC operation fails closed with the display off; a5ms stop/disable timeout resets only the ADC so a wedged conversion cannot indefinitely block system sleep.

## Home USB programming

No USB-to-UART adapter or application bootloader is needed for the selected MCU. A USB data cable and STM32CubeProgrammer provide the intended home workflow. ST publishes macOS builds, including Apple Silicon support; this repository has not exercised a physical Mac-to-Q4 DFU connection. [STM32CubeProgrammer](https://www.st.com/en/development-tools/stm32cubeprog.html), [UM2237](https://www.st.com/resource/en/user_manual/um2237-stm32cubeprogrammer-software-description-stmicroelectronics.pdf).

1. Verify the Q4 build manifest. Use the Q4 FRAM image, never Q3 firmware or the EEPROM alternate.
2. Enter the factory ROM by having the count-reset key (BOOT0) held at the moment reset is released. The order matters:
   - **Battery attached (normal update):** press and hold the recessed NRST pinhole switch first. While NRST is held, press and hold the count-reset key, release NRST, then release count-reset once the DFU device appears. Do **not** press count-reset before NRST: the running application treats the first debounced press as a count reset and saves zero immediately. Connecting USB does not reset a battery-powered MCU, so "hold count-reset while connecting USB" only zeroes the count in this state ([#3](https://github.com/dudgeon/count-fidget/issues/3)).
   - **No battery attached (USB-first commissioning):** hold the count-reset key while connecting USB; power-on then samples BOOT0 high. USB power supplies the board during programming.
3. In CubeProgrammer select USB, refresh and connect to the detected DFU device. Use ordinary readout protection (RDP AA), normal Bank1 boot (BFB2 clear) and nBOOT1 set. These are checked by the application.
4. On first provisioning, configure **BOR4** and read it back. The raw `BOR_LEV` field required by the application is **0xC**. RM0376 names this encoding "BOR LEVEL 5" (threshold VBOR4, 2.68–2.85 V falling); an entry labelled "Level 4" is raw 0xB and is wrong. Confirm the tool's displayed level/encoding rather than assuming every GUI uses the same label. With any other value the application never powers the display or touches the FRAM, so an unprovisioned board looks completely blank ([#6](https://github.com/dudgeon/count-fidget/issues/6)). Applying option bytes resets the MCU; keep BOOT0 asserted through that reload if continuing in ROM. Do not enable readout protection or change unrelated options.
5. Download `count-fidget-Q4-stm32.hex`, or the equivalent BIN at **0x08000000**, and run the tool's verification. The image does not include any EEPROM or option-byte data. Normal updates do not require a mass erase, FRAM initialization or protection changes.
6. Release the count-reset key if it is still held, and reset normally. On new/unrecognized FRAM, press count reset once during normal operation to establish a verified zero. For an update with valid FRAM, confirm the previously saved count returns.

The external FRAM is not in the ROM DFU address space used by this application download. Updating only this image therefore leaves its count records untouched. The application does not erase them at boot. Do not use reset/initialization as part of an ordinary update. If the application remains blank after an interrupted flash, repeat the hardware BOOT0/NRST entry; the immutable ROM is independent of the application image. SWD remains a second recovery route.

## Build and evidence

`firmware/q4-stm32/build/` contains the actual ARM ELF, Intel HEX, raw BIN, link map, disassembly, stack usage, host-test log and source-bound build manifest. `scripts/build_firmware_q4.py --verify-only` rechecks inputs, outputs, vectors, RAM budget and exact load equivalence. The manifest records the free Arm GNU 14.3.Rel1 archive, exact ST/Arm headers, actual included compiler headers and libgcc hash. It is reproducible engineering evidence, not a signed update mechanism.

Tests link actual portable production C to deterministic models of raw input, storage and bus transfers. Full tests enumerate 1,179,648 torn-word reboots, 256 single-bit record corruptions, 7,072 button waveforms, 2,295 queue/storage schedules, 200 recovery interleavings, 350 FRAM transaction/byte-prefix failures, 1,000 FRAM sleep/wake guards, eight permanent-fault inactivity/recovery scenarios across timestamp wrap, two failed FRAM sleep/wake retry-suppression cases, OLED startup/frame failures and voltage/error corners. UndefinedBehaviorSanitizer runs use a representative 257-step tear sweep while retaining the other suites. AddressSanitizer could not be exercised here: even a trivial instrumented program did not complete in this environment; that is not a passing memory-sanitizer result. Results and exact source hashes live under `verification/q4-firmware-*.json`; inspect those files for current counts and passes.

Unmodeled gates include compiled ISR latency on silicon, oscillator corners, peripheral errata behavior, brownout/rail sequencing, charge-pump and input timing, regulator/OLED transients, capacity/runtime, EEPROM physical tear behavior, FRAM rail-ramp compliance, USB enumeration and real repeated update/recovery. Hardware testing must include both keys during rendering, every sleep transition, NRST while FRAM sleeps, power interruption during commit, removal during OLED operation, minimum-cell display shutdown and the final exact stock parts.
