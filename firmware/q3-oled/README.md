# Q3 OLED firmware candidate

**For the separate Q3 hardware only. Do not flash onto Q1 or Q2.** Exact intended display: Wisevision **X087-2832TSWIG02-H14**, JLC/LCSC **C18723015**, SSD1312, 128 × 32 pixels. No physical board or display has been tested; this is neither a manufacturing release nor a current/runtime guarantee.

## Hardware contract

| Signal | MSP430FR4133IG48R | Meaning |
|---|---|---|
| Increment / reset button | P1.0 / P1.1 | Existing active-low inputs and external pullups |
| OLED_ENABLE | **P1.2, pin 24** | High enables the regulated **4.0 V** pump supply and its VBAT isolation switch; external pulldown holds it disabled during reset |
| OLED_RESET_N | **P1.3, pin 23** | Low asserts display reset; external pulldown |
| OLED_SDA / OLED_SCL | **P5.2, pin 28 / P5.3, pin 27** | eUSCI_B0 I²C, external pullups to the permanently supplied 3.0 V logic rail |

OLED VDD stays at 3.0 V during sleep. OLED VBAT must float when disconnected; do not add active discharge to that pin. The 4.0 V pump rail replaces the initially considered 3.7 V: the controller's 9 V pump guarantee requires VBAT ≥3.8 V, while this module limits VBAT to 4.2 V. The hardware review must cover regulation tolerance/transients. The intended external IREF resistor is **750 kΩ, 1%**. The firmware uses external IREF (`AD 40`), 9 V pump selection (`8D 72`) and initial contrast `10h`. Contrast is not a hardware current limiter.

The source assumes the bonded module's address is **0x3C** (7-bit, SA0 low). The controller supports 0x3C/0x3D; the module has no exposed SA0 pin. Verify its actual bond/address, acknowledged writes, segment remap, 16-row offset and orientation on hardware. A wrong address causes bounded retry while count saving continues.

## Behavior and scheduling

- Eight right-aligned digits, 0–99,999,999, no leading zeroes. `MAX` remains visible at the limit, including after restoring that count. No wraparound. Existing reset priority, held-key behavior and 30-second inactivity rule are unchanged.
- `counter.c`, `counter.h` and their existing host test are byte-for-byte copies of the shared Q2 counter/journal implementation. Information FRAM at **0x1800–0x181F** keeps the same two-slot version-1 journal. The application image excludes the entire **0x1800–0x19FF** information region. Factory initialization is separate; normal firmware updates must preserve it.
- Timer and port-edge interrupts capture raw button levels with timestamps into a 64-slot ring (63 usable samples). Foreground consumes up to eight samples per iteration using their original timestamps, then retries journal saving before display work. This preserves a complete press that occurs during a slow journal/render step. Interrupts never write FRAM or run display rendering. Queue reads and the final empty/overflow check before sleep are atomic.
- If captured history overflows, the device displays `ERR` with the retained count and suppresses further increments. A fully debounced reset commits zero before clearing the error. Actual held-button debounce state continues through recovery, so releasing reset while holding increment does not create a new press. The gap marker at **0x1820–0x1821** is written and read back in the foreground; any value other than `FFFF` restores the error after reboot. Failed marker writes retain the in-memory error and retry; failed clears retain the error. Abrupt power loss before a new gap marker can be written remains a physical persistence limitation.
- Only successfully committed counts enter the display. The existing two-slot journal layout/format remains unchanged; its new adjacent error marker is separate. Journal failures do not freeze interrupt sampling or display power management.
- I²C runs through interrupt-driven transfers, nominal **65.536 kHz**, at most **27 bytes** for initialization or **16 display bytes + control byte** per data packet. There is no framebuffer or 512-byte busy wait. A frame has a stable count snapshot; changes arriving mid-frame are coalesced into the next frame. One decimal digit conversion occurs per state-machine step. Unchanged counts send no repeated frame.
- No startup/transfer/retry/shutdown wait blocks the foreground. A bus failure or stuck SCL/SDA uses a nominal **20 ms** timeout threshold checked by foreground polling, holds reset, observes a **105 nominal ms** guard, switches off VBAT, and retries after one second while awake. Polling latency can extend the timeout; the input queue continues to capture samples. No open-ended oscillator-lock loop is used.
- Startup holds reset through a **23 nominal ms** stabilization interval plus 2 ms, releases reset and waits another 2 ms, initializes the controller, clears all eight controller RAM pages, enables the internal 9 V pump, then issues display-on. The visible-start guard is **105 nominal ms after acknowledged completion**; actual visibility/startup latency remains to be measured.
- Normal sleep sends `AE`, then `8D 10`, then waits **105 nominal ms from observing acknowledged completion** before cutting VBAT. Guard timestamps use a fresh HAL clock read after the action/completion, so a delayed foreground poll cannot shorten the interval. At the specified +3.5% fast REFO corner, allowing 1.01 nominal ms for tick phase, `(105−1.01)/1.035 > 100 ms`; the 23 ms startup guard likewise exceeds 20 real ms. These timing margins assume the specified clock behavior and do not replace rail measurements. VDD remains powered. Reset is held low after shutdown. A new press during shutdown is counted immediately and restarts the display after shutdown finishes.
- The MCU enters LPM0 during I²C transfers, LPM3 between foreground steps, and LPM4 only after the display is fully off, debounce is settled and the journal is clean. Port edges wake it on both press and release, including a held-key release.

The portable tests establish logic behavior, not target scheduling latency. The ring can retain 63 timer samples, fewer elapsed milliseconds during repeated edge interrupts; sustained overload is explicitly reported rather than silently accepted. ISR execution time, minimum accepted physical pulse width, I²C rise/hold timing, DCO/FLL behavior and worst-case journal/render execution must be measured on the target. The panel may show a partially transferred frame; FR synchronization is not exposed by this module and tear-free updates are not claimed.

## Sources and unresolved display details

- [Wisevision module listing and manufacturer datasheet](https://www.lcsc.com/product-detail/C18723015.html): Ver A drawing dated 2022-09-13; pages 6, 8–15 provide pins, module limits, application circuits and scan settings.
- [Solomon SSD1312 Rev 1.2, March 2021, hosted by Osptek](https://admin.osptek.com/uploads/SSD_1312_1_2_6a7ea26d1f.pdf): §6.1.5 I²C framing/address; §6.9.2 printed p25 reset/power sequencing; DC table printed p28; command table and §2.1.22 pump settings. The complete manufacturer-hosted PDF was downloaded and inspected; its hash and the exact module PDF's hash are in `source-records.json`.
- [TI MSP430FR4133 datasheet](https://www.ti.com/lit/ds/symlink/msp430fr4133.pdf) and [family guide](https://www.ti.com/lit/ug/slau445i/slau445i.pdf): GPIO multiplexing, eUSCI byte-counter automatic STOP, FRAM protection and clock/timer architecture. Build uses exact TI GCC **9.3.1.11**, support **1.212** headers/linker files.

The module's sample labeled “external” nevertheless uses `8D 12`, which the controller explicitly defines as **7.5 V internal pump**. Its example also has a 1/28 comment beside `A8 1F` (32 multiplex). Q3 follows the exact controller command meaning and the module's actual 128 × 32 geometry, not those contradictory comments. The controller command table has an inconsistent enable-bit label; its explicit supported byte sequences and shutdown `8D 10` are used. Obtain vendor clarification and qualify actual panel voltage/current, startup, brightness, orientation, waveform and sleep leakage before release. The separate cell/protection, charger/thermal, assembly/fit, brownout and other engineering gates remain open.

## Build and verification

Run `python3 scripts/run_host_tests_q3.py` for portable tests. Run `python3 scripts/build_firmware_q3.py --toolchain <TI-GCC-root> --support <TI-support-root>` for target compilation. Output lives only in `firmware/q3-oled/build/`. `--verify-only` checks the stored input/output hashes, ELF/HEX byte equality, actual interrupt/reset vector targets, program memory range, information-FRAM exclusion and preservation of Q1/Q2 images.

The build manifest binds source/header/test/build-recipe bytes, compiler/toolchain/support identities, transitive compiler dependencies, generated image/listing/map bytes and test output. Compiler stack-usage output is included; it is not a measured maximum runtime stack. The host suite covers existing debounce/journal/power-cut cases plus startup/clear/pump command ordering, dirty/coalesced rendering, saturation/error labels, 150 committed presses during repeated simulated bus timeouts, the missed-reset regression during a nine-millisecond foreground stall, 1,000 queued press batches across ring wraps, overflow, marker-write/clear failures and reset recovery, held increment through recovery, time wrap and early-startup sleep.

### Factory initialization versus ordinary updates

`build/factory-blank-info-Q3.hex` is a **factory-only** initializer: it writes `FF` to exactly **0x1800–0x1821**, clearing both the 32-byte journal and the new two-byte error marker. It intentionally resets the saved count. For a fresh Q3 device, load and verify this initializer separately, then load the Q3 application. Do not use an older 32-byte initializer alone, and do not flash this initializer during an ordinary firmware update. Ordinary updates load only the application HEX and preserve all information FRAM, including the error marker. The build verifies the initializer's exact range/bytes and hashes it independently of the application. Programming/test release remains subject to the coordinated Q3 hardware qualification and approved order.
